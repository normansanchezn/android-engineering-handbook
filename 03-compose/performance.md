# Performance

## Summary

Compose is fast by default. Performance problems almost always come from two sources:

1. **Too many recompositions** — a composable recomposes more than it needs to
2. **Expensive work inside composition** — allocations, heavy calculations, or I/O called during the composition phase

---

## `remember`

Cache values that are expensive to compute and don't need to change on every recomposition.

```kotlin
// ✅ Computed once, reused across recompositions
val formattedDate = remember(timestamp) {
    DateTimeFormatter.ofPattern("MMM d, yyyy").format(timestamp)
}

// ❌ Recomputed on every recomposition
val formattedDate = DateTimeFormatter.ofPattern("MMM d, yyyy").format(timestamp)
```

`remember(key)` — recomputes only when `key` changes. Omit the key only if the value should never be recomputed.

```kotlin
// Recalculates only when items changes
val totalCount = remember(items) { items.sumOf { it.quantity } }
```

---

## `derivedStateOf`

When deriving a value from state, use `derivedStateOf` to avoid unnecessary downstream recompositions.

```kotlin
val listState = rememberLazyListState()

// ✅ Recomposes only when the boolean changes (not on every scroll offset change)
val showFab by remember {
    derivedStateOf { listState.firstVisibleItemIndex > 2 }
}

FloatingActionButton(
    onClick = { /* scroll up */ },
    modifier = Modifier.alpha(if (showFab) 1f else 0f),
)
```

Without `derivedStateOf`, `showFab` would be a computed Boolean but the composable that reads `listState.firstVisibleItemIndex` would recompose on every scroll frame.

## Lazy Lists

| Practice | Why |
|---------|-----|
| `key = { item.id }` | Compose tracks items by identity, not position — avoids full-list rebind on item insert/remove |
| `contentType = { item.type }` | Compose recycles item compositions by type — improves scroll performance with heterogeneous lists |
| Avoid nesting `LazyColumn` inside `LazyColumn` | Nested infinite-height lists conflict; use a single list with header/footer items or `item { }` blocks |

```kotlin
LazyColumn {
    item { HeaderSection(uiState.headerText) }

    items(
        items = uiState.groups,
        key = { group -> group.id },
        contentType = { "group_item" },
    ) { group ->
        GroupCard(name = group.name, onClick = { ... })
    }

    if (uiState.isLoading) {
        item { LoadingIndicator() }
    }
}
```

## Avoiding Expensive Work in Composition

Composition runs on the main thread. Never do I/O, database queries, or heavy CPU work inside a composable.

```kotlin
// ❌ Network call inside composition
@Composable
fun AvatarImage(userId: String) {
    val bitmap = downloadBitmap(userId) // blocks main thread
    Image(bitmap = bitmap.asImageBitmap(), ...)
}

// ✅ Load in ViewModel, pass result as state
@Composable
fun AvatarImage(avatarUrl: String?) {
    AsyncImage(model = avatarUrl, contentDescription = null)
}
```

## Baseline Profiles

For release builds, add a Baseline Profile to pre-compile critical Compose code paths.

```
// app/src/main/baseline-prof.txt (generated by BaselineProfiler)
HSPLcom/myapp/presentation/feature/home/HomeScreen;->...
```

Baseline Profiles cut Compose startup time by ~30% on first launch. Generate with `./gradlew generateBaselineProfile` after adding the Macrobenchmark dependency.

---

## Profiling

Use these tools before and after any performance change:

| Tool | What it shows |
|------|-------------|
| Layout Inspector → Recomposition Counts | Which composables recompose and how often |
| Android Studio Profiler → System Trace | Frame timing, main thread jank |
| Macrobenchmark | Startup time, scroll frame rate in a real device scenario |

---

## Rules

Always:

- `remember(key) { expensive() }` for any computation that depends on changing input
- `derivedStateOf` when filtering/transforming scroll state or large collections
- `key = { item.id }` in every `LazyColumn`/`LazyRow`

Never:

- Run database queries or network calls directly in a composable
- Use `remember` without a key when the value depends on a changing param
- Nest `LazyColumn` inside `LazyColumn` — use `item { }` blocks for sections instead
